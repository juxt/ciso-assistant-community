## HITL Requirements — What the Policy Actually Demands

There are two sources of truth: the prose policy (LIWP-POL-AI-001 §8) and the spec's `HITLArrangement` entity plus `invariant HITLClaimsMustBeSubstantive`. I will read both in turn, then apply them to the submission's claim.

---

### 1. Prose policy — LIWP-POL-AI-001 §8

The policy defines HITL at §2:

> **Human-in-the-Loop ("HITL").** An arrangement under which a **qualified human** reviews AI output **before that output is acted upon or transmitted**.

§8 then requires that the arrangement be **substantive**, and identifies the following factors the reviewer must consider when assessing substantiveness:

- Whether the reviewer has **sufficient context** to evaluate the output
- Whether the reviewer has **sufficient time** available for review
- Whether the reviewer has a **meaningful ability to reject or alter** the output before it is acted upon
- Whether the workflow design creates **structural pressure** that renders review nominal (e.g. queue volume, default-accept mechanics)

The prose policy explicitly warns that a review step that is present in name but not in practice does not satisfy the HITL requirement.

---

### 2. Spec — `HITLArrangement` entity and `invariant HITLClaimsMustBeSubstantive`

The spec models HITL as a first-class entity with the following fields and the critical derived value:

```
entity HITLArrangement {
    reviewer_role: String
    has_reject_ability: Boolean
    has_modify_ability: Boolean
    review_criteria_documented: Boolean
    estimated_review_seconds: Integer

    -- Derived
    is_substantive:
        has_reject_ability
        and has_modify_ability
        and review_criteria_documented
        and estimated_review_seconds >= config.minimum_review_seconds
}
```

The invariant then states:

**`invariant HITLClaimsMustBeSubstantive`**
> A submission that asserts `defined_hitl` as a satisfied control must have an associated `HITLArrangement` where `is_substantive = true`.

`is_substantive` is a **conjunctive derived value** — all four conditions must be true simultaneously. A single false element collapses the whole claim.

---

### 3. The four conditions unpacked

| Condition | What it requires | Notes |
|---|---|---|
| `has_reject_ability` | The reviewer can **stop** the output from being transmitted | Not just flag it retrospectively — rejection must be available **before** transmission |
| `has_modify_ability` | The reviewer can **materially alter** the output | Read-only access to a draft does not satisfy this |
| `review_criteria_documented` | There is a **documented standard** against which the reviewer evaluates the output | Ad hoc professional judgment alone is insufficient — criteria must be written down |
| `estimated_review_seconds >= config.minimum_review_seconds` | Review takes at least as long as the configured minimum | `config.minimum_review_seconds` is currently set to **15 seconds** as a placeholder — but note **open question `OQ-Hitl-Minimum-Time`**: the AI Governance Office has not yet set a substantive floor for advice-domain systems, so the 15-second placeholder may be revised upward |

---

### 4. Application to the submission's claim

The submission states: *"advisor reviews each draft."*

Mapping that claim against the four conditions:

| Condition | Submission evidence | Assessment |
|---|---|---|
| `has_reject_ability` | Not described | ❌ Not established — the submission does not say the advisor can block transmission |
| `has_modify_ability` | Not described | ❌ Not established — no indication the advisor can edit the draft |
| `review_criteria_documented` | Not present | ❌ No documented review criteria referenced anywhere in the submission |
| `estimated_review_seconds >= minimum` | Not provided | ❌ No time estimate given; cannot assess even against the placeholder threshold |

**Result:** `is_substantive` cannot resolve to `true` on the current submission. The HITL claim fails `invariant HITLClaimsMustBeSubstantive`.

---

### 5. What the sponsor would need to provide to remediate

To satisfy the invariant, the submission would need to supply — at minimum — a completed `HITLArrangement` record establishing:

1. The advisor's role and qualifications (supporting `reviewer_role` and the §2 "qualified human" requirement)
2. A description of the workflow step at which rejection is possible, and evidence that transmission is gated on that step (`has_reject_ability = true`)
3. A description of how the advisor modifies outputs — e.g. whether the draft is editable in the workflow tool (`has_modify_ability = true`)
4. A written document — even a short checklist — setting out what the advisor checks (`review_criteria_documented = true`)
5. An estimated average review time per output, which the AI Governance Office can then assess against `config.minimum_review_seconds` and the as-yet-unresolved **`OQ-Hitl-Minimum-Time`** floor for advice-domain systems

This invariant states that where a `DeploymentRegisterEntry` exists for a prior deployment that is **materially similar** to the submission under review, the conditions attached to that prior approval **must carry forward** to the new submission unless the reviewer explicitly documents why a condition no longer applies.

#### `rule PrecedentConditionsCarryForward` — procedure

If a comparable entry is found, the rule requires the reviewer to:

1. **Identify** the prior `DeploymentRegisterEntry` by ID
2. **List** each condition attached to the prior approval
3. **Determine** for each condition whether it is satisfied, still open, or inapplicable (with documented rationale)
4. **Attach** any unsatisfied carry-forward conditions to the current submission before issuing an outcome

Failure to perform this check where a comparable entry exists is itself a compliance gap — the reviewer cannot simply ignore a precedent because it is inconvenient.
